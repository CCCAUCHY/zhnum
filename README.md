# zhnum — 中文数值感知排序 locale

自制 glibc locale，让中文数字文件名按**数值**排序：

```
一 < 一十一 < 二十 < 一百 < 一千零一 < 一万 < 一亿
第一章 < 第二章 < 第十章 < 第十一章
```

`ls`、`sort` 与 GNOME 文件管理器均生效（glibc strxfrm 与 GLib 文件名排序两条路径同序）。

## 两个 locale 源

| 文件 | 角色 |
|------|------|
| `zhbase` | 默认排序源：汉字按 Unihan 笔画数 → 部首 → 仓颉 → 码点排序（简繁同块混排），兼容汉字与各族文字整块在后 |
| `zhnum` | `copy zhbase` + 数字槽：中文数字串注册为多字符排序元素，按数值排序 |

`zhnum` 编译时以 `zhbase` 为 copy 源，两者需同目录可见。

## 排序机制

- **数字串是单个排序元素**：简体（一千九百）、财务大写（壹仟玖佰）、口语形（两百、五万一）等读法各注册为一个 collating 元素，权重编码数值——整串按数值参与比较，不逐字拆开。
- **同值写法相邻、不等值**：一 < 壹（固定注册序），`strcoll` 恒非 0。
- **槽位分区**：序数（第X章、篇X）与量词（X章、X篇）各占独立权重槽，同族聚族、族内纯数值序；序数子族与量词子族不混排。
- **括号序数**：（上）=（前）<（中）<（下）=（后），值都落在 零 与 一 之间——篇零 < 篇零（上）< 篇零（中）< 篇零（下）< 篇一；全角/半角、圆/方括号同槽。
- **首字全局序**：拉丁 < 中文数值区 < 汉字（笔画序）< 兼容汉字 < 其他脚本；阿拉伯数字按脚本自然位排（GLib 文件名路径下恒最前）。
- **别名**：一个数值的全部中文写法都是它的别名——四种风格（全小写 / 全大写 /
  小写数字+大写单位 / 大写数字+小写单位）各带简繁一套，由「数字类 3 形 ×
  单位类 4 形」的别名闭包展开（见 How it works）。例如 一百万 的 8 种写法：
  一百万 / 一百萬 / 壹百万 / 壹百萬 / 壹佰万 / 壹佰萬 / 一佰万 / 一佰萬。
  类内混写视为错拼，不在册。

## 三档 × 两版本

档位决定**完美排序范围**（档内全部读法严格数值序；超出档位的值退回多原子
近似，不差于系统默认序）；版本决定**注册哪些别名写法**（见 How it works）。

| 档 | 完美排序范围 | 版本 | 排序元素 | Nautilus 500 文件 |
|----|------------|------|---------|-----------------|
| `tiers/亿` | 10⁸ | `pure` | 128,234 | 11 ms |
| `tiers/亿` | 10⁸ | `mixed` | 320,981 | 19 ms |
| `tiers/万亿` | 10¹² | `pure` | 169,538 | 17 ms |
| `tiers/万亿` | 10¹² | `mixed` | 431,477 | 30 ms |
| `tiers/亿亿` | 10¹⁶ | `pure` | 210,842 | 25 ms |
| `tiers/亿亿` | 10¹⁶ | `mixed` | 541,973 | 45 ms |

`zhbase` 六份内容相同，仓库里只放一份（`tiers/zhbase`）。万亿/亿亿 的
`mixed` 超出 GitHub 单文件上限，以 `zhnum.gz` 入库（`gzip -d` 即得）。

**性能上建议搭配 Nautilus（GNOME Files）使用**：数值槽在权重2 带影子（见
How it works），中文数值区的键从第 2 字节起才有值——在这条路径上整组排在
阿拉伯数字段与拉丁之后（阿拉伯 < 拉丁 < 中文连块 < 其他脚本），与 Nautilus
的排序机制恰好衔接。Nautilus 对文件名中的阿拉伯数字段做自然排序自编码
（`2.txt < 10.txt` 与 locale 无关），数字段之后的文本段才交给 locale 比较，
天然适合元素量大的 locale；且它逐键缓存排序键，滚动大量文件时性能扛得住。
上表耗时即该路径的实测口径：每个文件名算一次排序键（逐键缓存）再按键比较，
500 个长名（平均 18 字）三档分别为 19 / 29 / 45 毫秒。
CLI 的 `ls`/`sort` 走 glibc strxfrm 路径，全量展开每个名字，元素量大时明显
更慢——本 locale 面向的是文件管理器，不是让 `ls` 变快。

## 构建

```bash
# Unihan 数据（笔画/部首/仓颉三张表；退出码 0=有更新 2=无变化）
python3 update-unihan.py .

# 补齐版 charmap（glibc 的 UTF-8 charmap 漏收若干兼容汉字码点，缺了它们
# localedef 会静默丢弃对应 locale 行——成因见 gen-charmap.py 头部注释）
python3 gen-charmap.py charmaps

# 生成（参数：档位上限 / 输出目录 / 写法版本）
#   档位  10**n，完美排序范围的量级
#   版本  mixed = 四种风格全注册（默认）；pure = 只注册全小写/全大写两套，
#         元素数约一半。见 How it works 的「别名」节。
python3 gen_zhnum.py 100000000 out/亿 mixed

# 编译 + 验证（charmap 必须用补齐版）
cd out/亿
localedef -f ../../charmaps/UTF-8 -i $PWD/zhbase ./loc/zhbase.UTF-8
localedef -f ../../charmaps/UTF-8 -i $PWD/zhnum  ./loc/zhnum.UTF-8
cd ../..
LC_ALL=zhnum.UTF-8 LOCPATH=$PWD/out/亿/loc python3 verify.py   # 末行应显示「全部通过」

# 或一键六份（三档 × 两版本：生成 charmap → 生成 → 编译）
./build_tiers.sh
```

构建数据：`unihan-strokes.tsv`（kTotalStrokes，基本区）、`unihan-radicals.tsv`（kRSUnicode）、`unihan-cangjie.tsv`（kCangjie，BMP）；脚本行基表取自系统 `/usr/share/i18n/locales/iso14651_t1_common`。

## 产物

`tiers/` 下是 glibc locale **源文件**——`localedef` 的输入：

```
tiers/
  zhbase                  默认排序源（汉字单块 + 兼容汉字 + 脚本行）
  <档>/<版本>/zhnum        数字槽排序   <档> ∈ {亿, 万亿, 亿亿}  <版本> ∈ {pure, mixed}
  <档>/<版本>/zhnum.gz     同上，仅因超出 GitHub 单文件上限而压缩，`gzip -d` 即得
```

`zhbase` 六份内容相同，仓库里只放一份。`zhnum` 用 `copy "zhbase"`，
**编译时两者须同目录可见**。源文件是 UTF-8 文本，编译需带补齐版 charmap
（`gen-charmap.py` 生成，见构建段）。

**编译耗时随元素量增长，慢不等于文件坏了**：`pure` 各份秒级到十几秒；
`mixed` 明显更久——`万亿/mixed`（431,477 元素）在一台普通桌面机上约
**351 秒**、内存变化几百 MB，元素最多的 `亿亿/mixed`（541,973 元素）更久。
耗时由元素量决定，与文件是否完整无关。

**怎么部署与本仓库无关**——放哪个目录、何时重编、给哪些程序用，各系统不同，
自行决定。

## How it works

### glibc locale 排序机制是怎样被利用的

glibc 的 collation 定义（就是 `iso14651_t1_common` 那类文件）允许声明
**多字符 collating 元素**：`reorder-after` 指定锚点，随后一行行注册
`<字符序列>;<权重1>;<权重2>;<权重3>;<权重4>`。strxfrm 把字符串展开成权重
序列，比较即逐权重字典序。

本项目的杠杆在于：**把每个中文数字读法注册成一个元素，权重直接编码数值**。
「一千九百」不再是四个汉字逐字比较，而是一个原子，权重序列把它放在所有
≤1900 的读法之后、所有 ≥1901 的读法之前。排序从「字典序的巧合」变成
「数值的必然」。

四个权重层各有分工（键按 权重1 → 权重2 → 权重3 → 权重4 逐层裁决）：

- **权重1**：负责按默认排序（zhbase）对首字进行第一次分区——汉字取 zhbase
  单块笔画序权重，数字槽与拉丁在这层透明（IGNORE）。骨架相同的短语（一篇/
  篇一/十篇）权重1 恒等，聚族由此而来。
- **权重2**：位置分区——数值槽在这层放槽值影子，汉字行放基表符号 `<BASE>`，
  骨架先行的子族在前（篇十 < 一篇），序数子族与量词子族分开。这层同时决定
  GLib 文件名路径的键形（见上文 Nautilus 段）。
- **权重3**：全部 IGNORE——刻意不承载任何值。基表用这层区分大小写与小型
  字形；数值槽若在这层带值，会在数值裁决前插入一层与基表不对称的比较，
  打断位置分区。空着，就是它的功能。
- **权重4**：数值本值——槽值在这层按值序排列（亿级单位在千级单位之前），
  并借基表的 position 修饰逐原子比较位置：序数/量词族内纯数值序，前缀对
  正确（第十章 < 第十一章）。

### 为什么依赖 zhbase 的权重2 与权重4

zhnum 的位置分区要求在权重2 和权重4 两个列上，汉字恒小于数值槽。这个保证
zhnum 自己的 reorder 块给不了——glibc 的权重分配序是：

```
基表符号 < 本地 reorder 新符号 < copy 链块符号
```

zhnum 的数值槽是本地 reorder 新符号，而 zhbase 的汉字行是 copy 链上的块。
汉字行若用自己的 token 作权重，会被数值槽符号整体压过，列方向反过来
（汉字 > 数值槽），位置分区翻车。所以 zhbase 的汉字行在这两层**借用基表已有
的符号**：权重4 借 `<U0021>`（`!`，基表低权标点），权重2 借 `<BASE>`（基表
自带的 collating-symbol，即假名 あ 行的二级）。位置机制必须在两级同时成立：
权重2 管位置分区，权重4 管数值序，任何一层列方向翻转都会在各自裁决层先出错。

另一个细节：权重位必须引用 collating-symbol（如 `<BASE>`），不能引用字符
token。字符 token 写在权重位不是「引用该字符的值」，而是给这个元素**新分配**
一个值——实测把 `<U3042>`（あ）写在权重位上，它被分到值域高位，并重排整个
值空间。

换个默认排序（比如拼音序）只需重写 zhbase、保持这两条契约，zhnum 的数值
机制自动跟随。

### zhbase 的默认排序：同部首、不同位置

zhbase 块内键序：笔画数（kTotalStrokes）→ 部首（kRSUnicode）→ 仓颉
（kCangjie）→ 码点。部首一级有个值得说的细节：Unihan 的 kRSUnicode 条目
形如「部首号.残余笔画」（章 = 117.5），**同部首、不同位置**的字带撇号标注：

- 单撇号（鸭 = 196'.5、驾 = 187'.5）表示部首不在该部首的常规位置——鸟部
  通常在下（鹭 196.13），鸟在右的 鸭 就标 `'`；马部通常在左，马在下的
  驾 就标 `'`。而右位属常规的部首不标：刂（刚 18.4）、攵（教 66.7）、
  阝（都 163.9）。
- 双撇号（鼡 = 208''.0、齢 = 211''.5）是简繁代理字——部首数据与正字重复，
  跳过部首条目（这类字仍经笔画表进块，按无部首处理，排同笔画桶末尾）。

生成时把单撇号剥掉，按「部首号 + 残余笔画」归组：**同部首不同位置的字聚在
同一个部首组里**（鸭 与 鹭 同在 196 组），不按位置拆散。效果：同笔画的字按
部首聚簇，同部首内按残余笔画、再按仓颉、最后码点定序；简繁同块混排（车 与
車 同笔画同部首，紧邻）。

### 101 倍与它的数学结构

档位内逐值注册的元素数是 O(档位值) 的——1e16 档那样要千万级元素。但中文数词
有**乘法分解结构**：

```
N = Σᵢ cᵢ·uᵢ    (cᵢ 系数 ≤ 9999, uᵢ 单位 亿ⁱ)
```

同一套系数 × 单位的**乘积读法可以复用**：「三百万」「三千亿」「三亿亿」共享
同一个系数槽模板，只有单位锚不同。于是**读数**数从 O(值) 降到 O(系数 × 档内
单位数)；每个读数再经别名闭包展开成 4~8 种写法（见下节），三档最终落在
32 万 / 43 万 / 54 万元素。

**101 倍的来源**：全量枚举在档位单位上只枚举到系数 r=1（r=2..9999 靠 COEFS
基座）。第一个「非基座系数」是 101（一百零一）——它是第一个带 零 的系数
（一百 与 一十 之间的非整十值）。于是任何档的完美排序边界都是
**101 × 档位单位**：亿档 = 1.01e10，亿亿档 = 1.01e18。这解释了为什么
亿亿档（名义 1e16）实测在 2.5e16 内零违例——语料里根本碰不到 1.01e18。

### 别名：一个数值的全部写法

一个数值的中文写法不止一种，它们都是**同一个值的别名**。写法由两个互相独立的
类决定，类内统一：

| 类 | 风格数 | 形 |
|----|-------|-----|
| 数字类 | 3 | 小写 `一二三…` / 大写简 `壹贰叁…` / 大写繁 `壹貳參…` |
| 单位类 | 4 | 小写简 `十百千万亿` / 大写简 `拾佰仟万亿` / 小写繁 `十百千萬億` / 大写繁 `拾佰仟萬億` |

十百千 的归类看前一个字：前面有数字时属单位类（一千 的 千），否则属数字类
（十万 的 十）。**简繁是单位类自己的轴**——`萬` 是繁体字而非财务字，所以简体
的全大写是 `壹佰万`（人民币壹佰万元整的写法），繁体的全大写才是 `壹佰萬`。

生成器只有一个闭包函数 `alias_closure()`，每个注册点调用一次即得该读数的全部
写法。这样安排的原因：**漏掉任何一种写法都不是"少一种写法"那么轻**——那串会
退化成多原子，而多原子的比较在**首原子**就终止，首原子携带的写法序会压过后缀
的数值：

```
壹仟零壹拾壹(1011)  vs  一千零一十(1010)
未注册时壹仟零壹拾壹拆成 [壹仟][零][壹拾][壹] — 首原子 = 壹仟 = 值 1000
1000 < 1010  ⇒  1011 排到 1010 之前  ✗
```

闭包对每个读数展开「数字类 3 形 × 单位类 4 形」，注册点上没有逐个列写法的
余地，也就没有"某别名漏注册"的可能。

**两套版本**：四种风格里，全小写与全大写是「同级配对」的两套（数字类与单位类
同级），另两套是混搭。`gen_zhnum.py` 的写法版本参数就按这条线切：

| 版本 | 含的风格 | 一百万 的写法数 |
|------|---------|----------------|
| `pure` | 全小写 + 全大写（各简繁）| 4 |
| `mixed` | 再加 小写数字+大写单位、大写数字+小写单位 | 8 |

`pure` 元素数约为 `mixed` 的 40%。**代价**：`pure` 版里混搭写法没注册，遇到时
会退化成多原子、因而可能错序——所以它是"常用写法够用"的取舍，不是等价精简。
要完整别名覆盖就用 `mixed`。

### 各种特殊情形的处理

- **同值写法**：一 / 壹 / 1 是三个**相邻但不等值**的元素（固定注册序），
  `strcoll` 恒非 0——保留「写法」这个信息，文件管理器里两种写法不会互相吞并。
- **序数 vs 量词**：「第十章」和「十章」数值相同，但 第 是序数锚、裸起句是
  量词锚，各自聚族不混排；「篇十」与「十篇」同理（序数子族恒在量词子族前）。
- **口语形**：两百、两千、五万一、二百五（=250）、三千六（=3600）各注册为
  其数值的单元素。
- **别名闭包**（数字一类、单位一类，类内统一）：一个数值的全部写法由
  「数字类 3 形（小写 / 大写简 / 大写繁）× 单位类 4 形（小写简 / 大写简 /
  小写繁 / 大写繁）」展开。十百千 前面有数字时属单位类（一千 的 千），否则
  属数字类（十万 的 十）；万亿 恒属单位类。简繁是单位类自己的轴——`萬` 是
  繁体字而非财务字，故简体的全大写是 `壹佰万`（人民币壹佰万元整），繁体的
  全大写才是 `壹佰萬`。类内混写视为错拼，不注册。
- **零的省略**：一万零一 与 一万一、一万零一十 与 一万一十 是**不同值**
  （10001 vs 11000/10010），省零读法独立注册各自的值。
- **简繁混排**：汉字默认排序（zhbase）简繁同块按笔画混排；数字槽里
  万/萬 同值相邻。
- **阿拉伯数字**：不进数值槽，按脚本自然位排（GLib 路径下恒最前）——
  Nautilus 自己对数字段做自然排序，两者正好衔接。

### 已知边界与尚无方法的优化

- **出档退化**：值超档位的串退回多原子近似——不比系统默认差，但不再精确。
  更高档位受元素数/表体积制约（亿亿档已 54 万元素）。指数级压缩（比如
  对超出 9999 的系数段用结构化规则而非枚举）需要 collation 权重层支持
  「条件规则」，glibc 语法没有这个能力。
- **贪心匹配的固有代价**：多字符元素匹配是贪心的，口语形会抢走同前缀的省零
  读法——实测 二万五十（20050）排在 二万一百（20100）之后（被 [二万五]
  (25000) 抢走首原子）；同类 二千零一（2001）排在 两千（2000）之前。
  已知限制，接受。
- **GLib 层 NFKC 折叠**：Ａ≡A、①≡'1' 等 GB 区字符被 GLib 归一化，locale
  层无法干预，实测影响为零（这类字符不出现在数字语境）。
- **未收录码点的回落**：基表 `iso14651_t1_common` 未定义、且不在 Unihan
  笔画表里的码点（谚文音节、CJK 扩展 A、私用区等）由 glibc 回落到「一~三级
  IGNORE」，互相 tie 并排在所有有序字符之前。系统 `zh_CN.UTF-8` /
  `en_US.UTF-8` 表现相同，非本 locale 引入，不处理。
  （兼容汉字是例外：它们属于中文区，见构建段的补齐 charmap。）
- **可能的未来方向**：把系数枚举上限从 9999 提到 99999999（覆盖 101 陷阱
  至更高档位）在数学上直白，但元素数同样线性增长；在 glibc 引入真正的
  规则化 collation 之前，枚举 + 复用是结构上更聪明的折中。


## 每周自动构建

`.github/workflows/weekly-rebuild.yml`（周一 04:23 UTC）：拉最新 Unihan → 重建三档 →
编译 + verify 全绿门槛 → 数据有更新时自动提交产物并上传 artifacts。

## 测试

`test/` 为样本文件名集（600+ 文件，覆盖下方全部情形）；`verify.py` 检测到该目录时
输出双路径排序结果。覆盖的情形：

- 阿拉伯数字（纯数字、年份/编号前缀、超长串）与英文（IMG_ 前缀、vN 后缀）
- 中文数值全拼写：一 < 二十 < 一百零一 < 一千零一 < 一万 < 一亿亿
- 财务四形：一千九百 / 壹仟玖佰 / 壹千玖佰 / 一仟九佰（及 貳佰萬、拾萬 等繁体形）
- 口语与两系：两百、两千、两亿、二百五（=250）、三千六（=3600）、五万一、两亿五
- 省零读法：一万一（11000）/ 一万一十（10010）/ 一万一百（10100）
- 序数/量词各族：第X章、第X集、第X册、篇X、X篇、X班、X回、X级、X季、排/列复合
- 括号序数：篇零（上/中/下）、三言二拍（前/中/后）
- 同值写法相邻：一 < 壹、万 < 萬、十万 < 拾万 < 拾萬 < 十萬
- 简繁混排默认序：车/車、龙/龍 同笔画块
- 档位边界：一百零一亿（亿档前沿）、十万亿、九千万亿
